# Changelog

## Unreleased

- Built-in tool `audio-studio` ([031](docs/workers/031-tool-plugins.md#audio-studio-music-and-sound-effects)): music, instrument loops and sound effects from Stable Audio 3 on the machine's GPU through audio-studio-mcp. Workers of an order that uses it get the `audio` server (generate, edit, process, unload) and a skill; Alba runs the operations `generate`, `edit` and `process` itself, one server process per job writing into the job folder. It holds `audio-gpu` (1 slot). Agent sessions no longer need the server in their own MCP configuration.
- Add machine-wide named locks, measured luminance and motion screenshot gates, image measurement commands, and streamed acceptance artifact receipts.

- Delivery lint `base_intact` ([009](docs/workflow/009-checks-and-waiting.md#optional-delivery-lint)): fails a branch whose HEAD puts files the base changed after the branch forked back to their fork-point content, the trace of merging `dispatch.base_ref` and then reverting that merge (`git revert -m 1`). Such a branch passed `base_merged`, because the base commits stay reachable, but merging it would delete work already merged. The finding (and the lint rework note) lists the files and the revert commits. It is on wherever `base_merged` is on; `base_intact: false` turns it off, `base_intact: true` turns it on alone.

- Foundations before content orders ([design intake](docs/libraries/030-design-intake.md#foundations-before-content-orders), [adopt Alba](docs/concepts/033-adopt-alba.md#3-write-the-foundations-before-the-first-content-order)). An optional `foundations` section in `alba.yaml` names, per set (`art: { kinds: [art, visual], tags: [], docs: [art-bible, palette, design/scale.md] }`), the documents a kind of work needs before its orders start: `design_docs` ids count when approved, project files when they have text. While a set is not ready, `mode: warn` (the default) lets matching orders start and every tick reports a `foundations` problem (in the console under **Foundations not ready**) naming what is missing and the orders going ahead without it; `mode: block` holds them back in the tick and refuses `alba run`, **Run now** and the producer's start with the same reason. `alba orders add` and a new order from the console (`foundationWarning`) or the producer say what is missing. An order tagged `foundation` writes the documents and is never held back. `alba foundations [--json]` lists each set, its documents and the orders it affects (exit 1 while one is not ready). Without the section nothing changes.
- `alba review <TAG> sheet` reports more than the mean ([006](docs/workflow/006-review.md)): per picture also the highlight share (luminance above 230 of 255), p5 and p95 luminance and the mean saturation, and, when `<name>.mask.png` lies next to the picture (white marks the subject), the subject's mean against the band around it, their difference and the subject's height in pixels. The earlier fields and their order are unchanged; masks are not put on the sheet themselves.
- The `art-pipeline` lesson pack has six more lessons from a project review whose weak art came from a missing foundation: `ALBA-ART-08` the art bible before the first content asset, `-09` generation settings checked on one sample against the shaders' channels before a batch, `-10` judging pictures by highlights, p5/p95 and subject contrast rather than mean brightness, `-11` consolidating a scene instead of stacking passes and no non-uniform scaling of delivered meshes, `-12` a licence line before any asset that was not generated, `-13` key art and the game side by side each milestone.
- The console has no Settings page: each part of the project file is edited on the page that shows it, behind an Edit button. Dispatch (caps by kind, stall, loop and lingering rules, merge, long commands) on Tick; resources and the workers file's quota sources on Workers; the skills every order and each kind gets on Skills; the lesson tags by kind on Lessons (new); budget and usage warnings on Usage; the clean rules on Clean.
- A Tools page in the console ([031](docs/workers/031-tool-plugins.md#in-the-console), [010](docs/console/010-api.md#additions-tool-plugins)): every tool plugin the project can see (image-gateway, tripo-3d, example-echo and the project's own) with whether it is on, its settings, its MCP servers and their tools, the environment variable names they read (set or missing, never the value), skill, CLI, probe, resources, paid operations and the kinds that use it, and the latest tool jobs. A tool is turned on or off, its settings, `plugins.by_kind` and `plugins.auto_approve` are changed from the page (`POST /api/config` now takes `plugins.enable`, `plugins.settings`, `plugins.by_kind` and `plugins.auto_approve`; never `sources` or `replace`), and **Check** runs the doctor (`POST /api/plugins/doctor`). `GET /api/plugins` is the read. The doctor no longer runs the probe and the CLI synchronously, so a slow probe does not hold `alba serve`.
- `alba serve` with several projects: no project waits for another. Each project has a thread of its own for its ticks, end checks, file polling and producer passes (one slow provision command, git call or quota command held up all of them). Projects share the workers file, and a worker's `concurrency` now counts the runs of every project: a tick counts the other projects' open runs on a worker, and a start records its run under a lock all projects' threads take, after checking the worker again (two projects could each fill a worker before). A start a person asks for on a named worker is not refused.
- The serve's end check no longer runs a PowerShell per open run every 5 s (about 2 s each, so seven runs kept the serve thread busy): repeated identity checks read one process table, read in the background for every process at once and refreshed every 30 s; recording the identity of a process just started still asks the system. Free memory is read with `os.freemem()` (the same reading, without a 3 s PowerShell per tick), and `git worktree list` is cached for 10 s.
- Usage accounting keeps the quota history in memory and reads only new readings (it parsed tens of thousands of them on every call), and a run whose quota share is settled is not worked out again with every new reading.
- Console reads: the board's view is built from each project's last real tick (a dry-run tick of every project took seconds after any change), with orders and the workers' running counts read now. Slow reads (clean plan, usage, skills, routes, lessons) have a reader thread of their own, so the pages polled every few seconds never wait behind them; more reads go to the readers, and file-change scans are coalesced.
- Editing from the console ([010](docs/console/010-api.md)): `GET`/`POST /api/config` read and change the editable sections of the project file and the workers file (dispatch settings and caps, resources, budget, clean, skills lists, lesson kind tags, routing and its worker groups, legacy roles, quota sources) in one write, with comments kept, a backup, and a check that the file loads and its routing resolves against the workers and every project; `GET /api/routing/migrate` gives the routing that replaces a file's roles; `POST /api/orders/<TAG>/fields` changes an order's title, kind, priority, worker pin, route, needs, tags, skills, resources, tools, heavy class, condition, check and review after it is made; `POST /api/orders/<TAG>/body` replaces its work-order text unless the file changed since it was opened; `POST /api/workers/<id>/remove` removes a worker nothing uses.
- The console no longer stalls while one page loads. `alba serve` answered the routes (`/api/roles`, with their results), the clean plan (`/api/clean`: git checks of every worktree, 20 s and more on a large project), skills, lessons, credits, resources and events on its main thread, so while one of them was worked out every other request waited, pages and the plain HTML included. They are read on the background reader like the other reads.
- A worker that has ended its turn and handed in its report no longer keeps its run open ([014](docs/workers/014-monitor-leases-loops.md)). When the last event of a run's log is the engine's own end (Codex `turn.completed`) and the final message holds a valid report block, the tick stops the process tree after 2 minutes, whatever `dispatch.on_lingering` says, and records the report; a `codex exec` had stayed after its last event while an MCP server held on, and the order sat in "running" with no events. `alba status` shows such a run as "turn ended, report handed in (ready); process still running" instead of its age. `alba orders run-end <TAG>` on a run whose log ends with its report records that report, instead of leaving the order without one.
- Routing above the workers ([012](docs/workers/012-routing-and-skills.md#routing-worker-groups-and-routes)). `routing` in the workers file or `alba.yaml` has worker groups (`groups`: ordered lists of workers, aliases, model families or other groups; the next one takes the order when the first cannot start; `"*"` at the end lets anyone else follow), routes that send kinds of work to a group (`routes.<id>: { kinds, group, requires, avoid }`), the group of the orders no route takes (`default`) and the workers no route chooses by itself (`avoid`, written once). Changing a group changes every route that uses it. A route only routes: `skills`, `mcp`, `rules`, `tools` and `effort` are refused with where they belong (`skills.by_kind`, tool plugins under `plugins.by_kind`, a skill, the launch template). `roles` keeps working; a file has one of the two. `alba routing` lists groups and routes and who qualifies now; `alba routing migrate` prints the routing that replaces a file's roles, choosing the same worker in every case, and where their skills, MCP servers and rules go. `alba route` names the group ("group main #2", "not in worker group main"). The console's Roles page is now **Routing**, with the groups first; "Role" reads "Route" on the order pages. `GET /api/roles` adds `groups`. The example workers file uses routing (and parses again: a note with a colon was not quoted).
- The console moves. The Machines page opens with a fleet map: this computer in the middle, the registry's machines around it with their memory and CPU, the workers that live on each and the runs out on them now; a line carries light out (branch, prompt, LFS objects) and back (commits) while a run is there, and a machine that does not answer hangs on a broken line. Pages and panels rise into place, numbers count up, running work glows, the logo's sun comes up and loading placeholders shimmer. Animations are on by default (the system's "reduce motion" is not followed: Windows sets it whenever its animation effects are off); the sparkle switch in the header turns them off for this browser. `Worker` in the API has `host`, the machine a remote worker runs on, shown on the Workers and Overview pages. The README describes the features and how scheduling across machines works.
- Editor pools prepare the worktree first ([032](docs/workers/032-run-editors.md#preparing-the-worktree-first)): `editors.<pool>.prepare` runs a command in the worktree before the editor starts (for example compiling a C++ game module a new worktree does not have), skipped when its outputs are newer than its inputs, tried again on listed exit codes, with its output in `.alba/editor-prepare.log`. An editor that stops before its MCP server answers is reported with the dialog text it logged ("the game module ... could not be found") instead of only "the editor exited".
- The console has no sign-in by default again: on one person's machine any browser and program there may use it, as before the key existed; other sites stay refused (`Sec-Fetch-Site`, the Origin rule for writes, the Host check and the CSP). `alba serve --sign-in` / `alba web --sign-in` turns the key, the sign-in link and the session cookie back on for a machine other accounts use. An old `/login` link goes straight to its page ([Access](docs/console/010-api.md#access)).
- Starting and stopping runs (review findings R-2, R-3, R-6 to R-12). A start checks the kind caps and resources again in the state transaction that records the run and takes its leases, before the worker is spawned: the tick and a person's `alba run` (or **Run now**) could both take the last slot, because leases were written after the spawn. The tick's own start may use the `rework_reserve` it planned, no more. A step after the spawn that fails stops what was started and ends the run as `failed`; a run Alba recorded that has no pid 10 minutes after its start is ended by the tick instead of staying open (a run a person opened with `orders run-start` is left alone). The tick releases leases in one transaction and claims an editor slot (`releasing`) before stopping its editor, so neither can undo a fresh start of the same order. A run whose process creation time could not be read at launch can be stopped: its process is the one created within its launch window (15 s before to 2 minutes after the run's start); before, it could never be stopped, and a reused pid kept it open. A monitored job whose process has ended is checked once more and handed back (`done`, `failed`, or `failed` because it is gone and neither condition held); it stayed `monitoring` for ever. `dispatch.on_lingering: stop` ends the run's process tree (the capture wrapper or editor helper was all it stopped) except the job its report hands to the monitor. On Linux and macOS a stopped process still there after 5 s gets SIGKILL. `.alba/bin/lock.mjs` writes its lock whole, takes over a lock left half written or held by a reused pid, does so under a second short lock (two waiters could both take a stale lock), and stops its command before giving the lock back. An order whose kind is also its heavy class counts once against that cap, and the tick counts editor ports on the machine of the run's worker (the pool's slots were summed over all machines).
- Producer review findings P-4 to P-12 ([024. Producer session](docs/producer/024-producer-session.md)). A chat's message id goes only to actions filed under that message's own case, and only such an observe-mode would-do (or a pending draft) can be run from the console: an action proposed for another case while a chat ran borrowed the id and became one click away. Accepting or sending back an order waiting for review needs the finished review of its current delivery (`work: <review id>`) whichever case the proposal names (another case got past the old check), and a work result becomes a proposal only after the router was shown it: its card now carries the finding and proposed action, and `producer_read kind work` reads the full result. Serve reconciles detached work every thirty seconds even with the router session off (a "draft again" never finished or was metered). A router turn that runs past `producer.session.turn_timeout_minutes` (default 15) is failed and the session restarted with a recovery note instead of holding every later card and chat back. With `budgets.cost_per_day_usd` set, a model without a price sends no turn and starts no work (its spend was never counted against the cap). Pausing the producer also stops router turns, handoffs and wanted-session starts. At most `producer.session.max_work_sessions` (default 3) detached work sessions run at once. `reprioritize` cannot drop a need that is not merged or make a dependency cycle. Accepting a draft keeps the order's worker and producer pin; the draft's worker hint only fills an empty one.
- Skills, plugins, packaging and quota (review findings T-9, T-12c, O-8, O-10). A role's additions no longer push out a skill someone else asked for: `skills.max_per_order` leaves out a role's own skills (the last first) and tag matches only, and always keeps Alba's rules, `skills.always`, `skills.by_kind`, a tool plugin's or editor's skill and skills named on the order ([012](docs/workers/012-routing-and-skills.md)). A plugin is its manifest `id`: a project plugin with a built-in plugin's id replaces it only when the project lists the id under the new `plugins.replace`, otherwise it is refused and enabling the id fails with the reason; of two project plugins with one id the first is used; a folder named otherwise than the id is reported ([031](docs/workers/031-tool-plugins.md#where-plugins-come-from)). Alba installs as a package: `npm pack` builds `src/` to `dist/` and the console first (`scripts/build.mjs`, `pnpm build`), `bin/alba.mjs` runs `src/` in a checkout and `dist/` when installed, and the package carries the plugins, templates, docs and examples the code reads ([README](README.md#install-as-a-package), [033](docs/concepts/033-adopt-alba.md)). A quota source of type `codex-sessions` reads a Codex subscription's windows (named by length, `5 hours`, `7 days`) and credit balance from the rate limits Codex writes into its own session files, calling nothing; Claude Code's stream-json carries no usage limits, so a Claude subscription needs a `command-json` or `static` source ([003](docs/workers/003-workers-and-quota.md#quota-sources)).
- Producer and paid-tool spend (review findings P-1, P-2, T-4, T-5). An auto action runs in one process only: the MCP server and `alba serve` both ran some twice, and rewrites of the whole action list from an old copy dropped actions and decisions other processes stored meanwhile; now each action is added or changed under the state lock and claimed before it runs, and one whose process died while running it is failed, not run again. `plugins.auto_approve` keeps a running total: a number is one job's cap and ten jobs' worth a UTC day, and `{ per_job, per_day, per_project }` names the totals of what Alba approves by itself (reserved under the state lock). Every paid call gets a quote and is booked: a price of 0, or a quote tool that says `unpriced: true` (Tripo's ceiling), makes a quote only a person approves. A paid call that was sent and then timed out, lost its connection, answered an error without saying what it spent, or whose files could not be written is booked as unknown, at most the quote (`unknown: true` on the ledger line), as is a job whose process died while it ran; the price is booked before the files are written, and a booking the state could not take is kept on the job for the tick. `image-gateway` and `tripo-3d` say `spent: 0` when they fail before anything paid was asked.
- Console access (review findings S-2, S-3, S-4, S-7): the write token was handed to any local process (`GET /api/session` and a `<meta>` tag in the page). Each start of `alba serve` or `alba web` now makes a console key that no answer contains; it is printed as a sign-in link (`/login?key=...`) and written to `console-<port>.json` in a folder only your OS account can read (`%LOCALAPPDATA%\alba\run`, `$XDG_RUNTIME_DIR/alba` or `~/.alba/run`; `ALBA_RUNTIME_DIR` overrides). A browser trades it at `/login` for an `HttpOnly; SameSite=Strict` session cookie; programs (and `alba producer session start` while serve runs) send it in `x-alba-token`. Every `/api` call and `/legacy` page, reads included, needs one of the two (401 `unauthorized` otherwise; the console and the old board go to `/login`). Requests another site or another port of this host makes (`Sec-Fetch-Site: cross-site`/`same-site`, which an `<img>` sends without an Origin) are refused before anything runs; browser writes must carry an allowed Origin. The old board's forms keep working and carry a token derived from the key instead of the key. The console page has a Content-Security-Policy (own scripts, inline ones by hash; no frames or other sites), project pictures and videos are served sandboxed, and the Vite dev proxy rewrites only its own page's Origin (it also passes `/login` and `/logout`). See [Access](docs/console/010-api.md#access) and SECURITY.md.
- Acceptance fixes from the same review. Approval is refused while a run of the order is open (it was allowed from `running`). A pipeline merge completes or rolls back to a recorded state: `<state_dir>/acceptance/merge-journal.json` names the base branch's old tip, the merge, the note and what the push changed; any failure (also one after the push, which only reset the local branch) puts the remote branch back with `--force-with-lease`, removes the note and resets the base, and a merge whose process died is rolled back by the next approval. The design change sets, the `accept-merged` record and the approve action are one state transaction, so a refused change set now rolls the merge back instead of keeping it; committed change sets are read from the merge commit and the others exactly as the trial saw them (they were read from the live worktree). A ready delivery with no commits of its own has to pass the pipeline trial (it skipped it as "already merged"). The files state backend rolls a transaction back like SQLite (a journal, `_write.journal`, also restores one cut short by a crash), and its lock (like the acceptance slots) is taken over from a dead owner safely: under a second short lock, only while it still holds the owner judged stale, also when a pid was reused, never from another machine. `alba sync` approves from a `<TAG>.accept.md` only a ready delivery with no open run; a leftover note next to a failed or blocked order needs a person's `--override`. `credits gate` holds what it lets through (until the spend with the same `--key`, or an hour), and `credits spend --key` books once (`POST .../spend` takes `key`); tool jobs hold and book under their job id. The blank-picture checks read JPEGs (at one value per 8x8 block) and interlaced PNGs: a black JPEG or a flat interlaced PNG passed.
- Fixes from a review of every subsystem. Security: a request path starting with `//` or a malformed Host header no longer stops the server (an `<img>` on any web page could); old-board forms check the Origin like the interface; requests must arrive within 30 s; a listed document at the project root no longer makes every `.md` of the project readable; a `.alba-skills.json` in a worktree can no longer make a skill mount remove folders outside its folder; the producer's router and work sessions load only the person's own Claude settings (`--setting-sources user`), not a project's `.claude/settings.json` with its hooks. Money: `image-gateway` `generate` is paid (one `images` per picture, quoted; `plugins.auto_approve.images` approves small ones) and its reference pictures must be picture files; the Tripo wallet has one slot (its spend is read from the wallet before and after). Runs and state: a run whose pid now belongs to another process (Windows reuses pids) is ended instead of kept open forever; a report block that cannot be read is a failed delivery instead of a guessed `ready`; a line of `events.jsonl` cut short by a crash is skipped instead of breaking every event read. Editors: an editor is this run's only when its command line has both the port and the worktree argument; a server already answering on the port that is not this run's editor fails the start instead of being driven; a slot whose editor could not be stopped is kept and retried. Capture scripts exit 1 when nothing was saved, no longer bring the window forward or copy the screen, and ignore exited processes; `frames.mjs` removes its temporary folder on a bad input.
- A new project needs less: with no `roles` every order may go to any worker; `dispatch.worktree_parent` defaults to `<id>-worktrees` next to the repository and `dispatch.base_ref` to `main`, else the branch the repository is on; a dry run checks the work-order file and the base branch; `orders add --queue` without a work-order file is refused; a worker without a launch template is not available, and a Claude worker that names no sign-in is warned about (it does not see the person's `claude` login: pass `CLAUDE_CODE_OAUTH_TOKEN` from `claude setup-token`); `skills.engine: other` leaves the engine skills out. [Adopt Alba in your own project](docs/concepts/033-adopt-alba.md) takes a repository from nothing to a first run.
- Alba's skill library and lesson packs, from what the first game project learned ([012](docs/workers/012-routing-and-skills.md#albas-skill-library), [library formats](docs/library-formats.md#lessons)). Built-in skills besides the core rules, attached only where a project, role, order or editor pool names them (never by a tag; a project's skill of the same name replaces them): `game-capture-windows` (PrintWindow still and clip scripts for the window of the process you started, and `frames.mjs` for contact sheets, mean luminance, black frames, flicker outside named cuts and identical files), `unreal-headless-pipeline`, `unreal-mcp-editor` (the run's editor over MCP; `editors.<pool>.skills` attaches it) and `alba-review-bar` (the store bar and the ways deliveries cheat; `producer.review_skills` puts a skill's text into the producer's delivery reviews). `lessons.packs` adds built-in lesson packs `unreal`, `windows-workers`, `art-pipeline` and `deterministic-sim` (ids `ALBA-<PACK>-<nn>`). The core worker rules add: new features in new files and small edits to shared files, and a **Done means** section (tests that can fail and drive the code, a real caller, never weakening an acceptance condition, measured claims, evidence a check rewrites).
- An editor for each run ([032. An editor for each run](docs/workers/032-run-editors.md)): `editors.<pool>` in alba.yaml names a game editor (program, arguments with `{worktree}`, `{port}` and `{log}`, the MCP URL) and fixed ports per machine. An order that uses the pool (`--uses ue-editor`) gets a free port of its machine; the worker is wrapped by `.alba/bin/editor.mjs`, which starts the editor on the worktree, waits until its MCP server answers `initialize` (`ready_minutes`, default 10; otherwise the run fails before the worker starts, with the reason), runs the worker with the server attached (Codex `mcp_servers.<name>.url`, Claude `--mcp-config` type `http`, OpenCode `remote`; `NO_PROXY` gains `127.0.0.1,localhost`) and stops the editor when the worker ends. The worker restarts its editor around a C++ build with `node .alba/bin/editor.mjs stop|start` on the same port. Editors are found only by the program and the run's port argument; the tick stops the editor of any ended run and gives the port back. The pool is a resource (one slot per port); an editor also holds the pool's `holds` and counts against its `cap`. The run records `editor: { pool, machine, port, url, log }`; `alba status` and `alba editors list | restart | stop` show and act on the slots.
- Built-in tools `image-gateway` (any OpenAI-compatible images endpoint: generations, and edits from reference pictures; the files keep their real size) and `tripo-3d` (Tripo Studio with the member account logged in on the machine: workers get its `tripo_*` tools and a skill; Alba's paid `generate-model` operation prices the model, falls back to a `ceiling` when Tripo cannot price it, follows the configuration form and the task, downloads the model and books what the wallet shows was spent). Plugins have `settings` (`${setting.x}` in commands, arguments, `env_from` and the probe; set in `plugins.settings`), servers for operations only (`workers: false`), and an operation's answer may say what it `spent`, which is booked instead of the price. `alba plugins doctor` checks an enabled tool with the project's settings.
- Tool operations and jobs ([031. Tool plugins](docs/workers/031-tool-plugins.md#operations-what-alba-runs-itself)): a plugin's `operations` (an input schema, an MCP tool or a program to run, an optional quote, the output files) are run by Alba itself with `alba tools run <tool> <operation>` and by the producer's new `tool-call` action (`producer_read` kind `tools` lists them). A job checks the input, prices a paid operation and makes a quote on the order (approved by a person, or by Alba within `plugins.auto_approve`), passes the credits gate, leases the tool's resources, keeps the outputs in `<state_dir>/tool-jobs/<job>/`, books the spend after the call and records every step as an event. The tick starts a job again once its quote is decided or its resource is free. `example-echo` has a free and a paid operation to copy.
- Workers cannot move the base branch: every worker process gets `ALBA_RUN=<TAG>/<run>`, and a local run installs a `reference-transaction` hook in the repository that refuses, while `ALBA_RUN` is set, any update moving `dispatch.base_ref` (a merge, commit, `branch -f` or `update-ref`, from the main checkout or a worktree). `git merge main` inside a worktree, other branches and `git gc` are not affected; the lead's and Alba's merges pass. Refusals go to `.git/alba-guard.log`. A claude-sonnet run had merged its branch into `main` in the main checkout; the outside-worktree check only reported such work afterwards. The hook is not installed over `core.hooksPath` or someone else's hook (the run records a warning).
- Tool plugins (first part of the [plugins proposal](docs/proposals/plugins.md); [031. Tool plugins](docs/workers/031-tool-plugins.md)): a folder with an `alba-plugin.yaml` (apiVersion 1) brings a tool's MCP servers with their allowed tools and the environment variable names they need, its skill, its resources and a probe. Built-in plugins live in `plugins/` (`example-echo`, a complete tool to copy); a project adds its own with `plugins.sources` and turns tools on with `plugins.enable`. An order uses the tools it names (`orders add/set --tools`) and those of its kind (`plugins.by_kind`): a run gets the servers through the role mount (Codex `enabled_tools`, Claude `--allowedTools` per tool), the skill, a lease on the tool's resources and a **Tools of this run** prompt section, and records `tools: [id@version]`. `alba plugins list | show | doctor` lists plugins and checks on this machine that the probe runs, the named secrets are set and each MCP server starts and offers the listed tools.
- Machine locks for workers: every worktree gets `.alba/bin/lock.mjs` (`node .alba/bin/lock.mjs capture -- <command>` waits its turn for a named lock of the machine). The worker rules have a section on game windows: capture only the window of your own process (PrintWindow or the engine's screenshot command, never a desktop region or a window found by title), under the `capture` lock, and open every picture you name.
- Evidence pictures a `ready` report names are checked: byte-identical copies under different names, and flat one-colour PNGs (black or blank captures), send the delivery back once with the files named (event `evidence-bounced`); a repeat goes to review with a warning.
- Work outside the worktree: every prompt names the worktree as the only place to work and the main checkout as the lead's (a claude-sonnet run worked and committed in the main checkout). A local run records the main checkout at start; a delivery whose reported commits were made directly on the base branch during the run becomes `blocked` with the commits and changed files (event `outside-worktree`); other changes there only warn.
- A worker a person names for a run (`alba run --worker`, **Run now**) becomes the order's worker (event `worker-set`): a rework queued afterwards was started by the tick on the order's old worker (REN4 went back to codex-paid past "presentation only on Claude"). `alba orders set <TAG> --worker <id>` sets it directly. `orders act <TAG> queue` on a held order releases it instead of refusing.
- Remote runs bring back the Git LFS objects a worker committed on the host: the sync lists the LFS files of the fetched branch, copies the objects the local store lacks from the host's bare repository, fast-forwards without smudging and fills the files with `git lfs checkout`. Before, those files came back as pointers (or the fast-forward failed) and `lfs_sync.py --pull` had to be run by hand.
- Remote runs on Windows hosts: a program that needs a window or the GPU's swap chain (a game capture) failed over SSH with `DXGI_ERROR_NOT_CURRENTLY_AVAILABLE`. The runner now ships `desktop-run.ps1` (`$env:ALBA_DESKTOP_RUN`), which runs a command in the logged-on user's desktop session through a one-off interactive scheduled task and passes back its output and exit code; the prompt of a run on a Windows host says how to use it.
- Checks: `encoding_scan` also flags JSON files the branch added or changed that start with a UTF-8 byte order mark (workers on Windows PowerShell wrote them; JSON readers refuse them), as its own item, so delivery lint sends them back.
- `alba review <TAG> sheet`: a contact sheet of the order's evidence pictures as one PNG, and per picture its size, mean luminance, spread and dark share, so a review starts with one image instead of opening each capture.
- Design change sets are checked when a run reports `ready`: a dry run of the apply acceptance does after the merge (nothing written). A set it would refuse goes back to the worker once with the reason (event `design-bounced`), while its session is still there; in the first game project almost every design delivery needed `--override` at approval (wrong `base_version`, `implementation` values, missing sources or evidence, unknown ids or blocks). A dry run no longer writes the library export.
- Adding an order with a taken tag says the stage of the order that has it (a merged or cancelled order keeps its tag) and suggests the next free tag like it (`FACT1` -> `FACT4`, `REN2A` -> `REN2C`), in `orders add`, `orders new`, the board and planned orders.
- `orders list` and the board show who has the order now (the open run's worker, the worker pinned for the next run, else the newest run's) instead of the worker the order was written for; `orders list --json` adds `current_worker`.
- `<TAG>.last.txt` and `<TAG>.progress.json` in a work-order folder inside the repository are kept out of git (`info/exclude`, set when a run starts): workers committed their progress files, and the untracked copies in the main checkout stopped `git merge` until a person moved them aside.
- Worker outbox: only a `question` puts a running order in front of a person (`awaiting-user`); a `blocker` or `note` while the run goes on is shown as unanswered without changing the stage, and a blocker the worker wrote anything after is past. `alba answer` to a question the open run wrote goes to its inbox as the reply (`--choice` picks one of the question's options) instead of recording an answer that only queued the order behind the run. Entries are timed by when alba picked them up (a worker's clock was a year off), a line with a byte order mark or without `at` is read instead of dropped, and the worker rules say to keep progress in notes and write without a BOM.
- `alba run` and the console's **Run now** respect the project's kind caps: five `ue` orders ran at once under `caps: { ue: 3 }` because only the tick checked them. A full cap refuses the start and names who holds it; `--over-cap` (API `over_cap`) starts it anyway; the API answers a refused start (cap or resource) with 409. Every prompt now ends with **Slots this run holds** (the cap slot and the resources of the run), so a worker whose rules say "build only if you hold the slot" knows it does (a Codex worker refused to build for an hour).
- Fixed remote orders getting Git LFS pointer files instead of assets: the branch is pushed without LFS content (the host has no LFS server), and nothing copied the objects, so the host's checkout left pointers (a worker deleted nine .uasset files it took for corrupt ones). The runner now copies the LFS objects the host's bare repository lacks into `<bare>/lfs/objects` before checkout, and a checkout that still leaves a pointer stops the dispatch before the worker starts (run failed: `remote dispatch failed` with the files).
- Fixed Codex orders stuck after `say --restart`: a new Codex session recorded an id the tool made up (Codex picks its own thread id), and a run stopped by a person never got the real one, so every resume failed with "no rollout found for thread id", also after the order was queued again. A resume now uses the session the engine reported in the previous run's events; "no rollout found" (and Claude's "No conversation found") is a lost session and the next start is fresh with the order and the messages; queueing again after a message, or another worker, starts a fresh session.
- Claude workers: a run whose last message has no report block takes the newest valid block of an earlier message of the run (a background command that ended after the final message made `claude -p` answer once more, and the run failed or was sent for repair), or a report the worker saved with the Write tool to a `*.last.txt` file; the run is marked `report_from` and the order gets a `report-from-earlier` event. Spacing inside the report markers is forgiven. The Claude prompt and the worker rules say to wait for or stop background commands before the final message.
- Producer: a planned order whose draft session failed is drafted again: the case goes back to the router and the host retries it on a later pass (two sessions under the current time limit, one an hour; failures under the old 120-second limit do not count). The order page shows the last draft session and its reason and has **Draft again** (`POST /api/orders/:tag/draft-again`). A rejected draft is not retried.
- Producer: accepting an `answer` card runs `alba answer` (the asking session continues on the same worker); it only recorded the answer, and the tick could then start another worker in a new session. The trust page counts your own `alba answer` to the same question as the decision of a pending answer proposal (same text: accepted; other text: edited).

## 0.1.0

First public release.

- Work orders with dependencies and acceptance criteria; stages worked out from facts, not set by hand.
- Worker dispatch into isolated Git worktrees, with process identity, start receipts, loop and stall detection, quotas and spend caps.
- Built-in adapters for Codex, Claude Code and OpenCode, a `script` worker for local programs, and a documented adapter interface for new engines.
- Report blocks, evidence, review, merge readiness and approval; a successful exit never approves an order on its own.
- Optional modules: producer, design library, art library, picks and credits.
- Machine registry with probes, engine modules for Unreal, Unity and Godot, tool installation plans and Windows SSH workers.
- Web console with light and dark themes and English and Chinese interfaces.
- Windows, Linux and macOS support, a local demo that needs no model account, and CI on all three platforms.
