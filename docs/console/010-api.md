# 010. The JSON interface

Uses the terms of documents 001 to 009.

## Producer activity (read only)

`GET /api/producer/config?project=<id>` returns `{file, found, yaml}`: the lines under `producer:` in the project file. `POST /api/producer/config {project, yaml, dryRun?}` replaces them: the new file is checked the way serve reads it (an invalid value is a 400 and nothing is written), the answer is `{file, changed, dryRun, diff, before, after, backup?}` with `diff` as `{op: ' ' | '-' | '+', text}` lines, and a write keeps a `.bak-<time>` copy. The rest of the file stays byte for byte. See [the producer settings](../producer/024-producer-session.md#rework-planned-orders-and-the-producer-settings).

`GET /api/producer/log?project=<id>` returns `{project, at, now, rows}`. Optional filters are `since=<ISO time>` (inclusive), `kind`, `order`, `status`, `autonomous=true`, and `superseded=true`. Superseded actions are hidden by default; explicitly filtering `status=superseded` also reveals them. Invalid `since` returns 400. Rows are newest first by execution completion, execution start, decision or proposal time, then stable id. Action audit duplicates are omitted; each action has one row reflecting its current recorded/validated status. Pause/resume, budget exhaustion and session start/stop/error audit events are merged into the same timeline. The API leaves UTC timestamps intact: the browser groups days in its local timezone, including daylight-saving boundaries.

Each row has `id`, `at`, `kind`, `status`, `mode`, `note`, `firstLine`, `evidence`, `claim`, and `autonomous`; optional fields are `order`, `case`, `result`, `rule` and `acceptance`. `mode` is `auto`, `proposed`, `observe`, `off`, or `system` for audit events. `autonomous` means an auto action with done/failed status and no recorded human decision. `rule` includes the recorded rule id and policy version; instruction text appears only when the recorded policy hash matches current policy. `claim` flags verification language in accept/rework notes, including English and Chinese, without evaluating truth. `acceptance` shows recorded merge and design-change-set step results in that action's execution window; missing historical facts remain absent.

`now` has a plain state key, optional reason/since/until/lastTurnAt/nextRoundAt, active cases (key, summary, optional order), and five budget entries (key, optional used/limit, resetsAt): hourly turns, daily usage, review runs, draft runs and escalations. Review usage combines independent checks and producer review/work runs. Counters and allowances reset at their UTC boundaries. Missing limits mean unbounded. The next round time is its earliest scheduled eligibility, subject to the serve polling interval; missing round history means due. A paused/disabled producer has no scheduled round.

Session recording fields: `_producer-session.json` stores `currentTurn` (oldest pending recorded turn, cleared when finished/stopped) and `budgetUntil` (the UTC budget boundary that paused it); actions store `completedAt` after attempted execution. Session lifecycle and budget pause transitions append to the existing `producer-audit.jsonl`. Unknown details are shown as unavailable. Reading this route never starts intake, refreshes analytics, reconciles a session, probes a machine or invokes a model.

`alba producer log [--since <ISO time>] [--json]` reads the same model. JSON returns the complete response; text emits one line per row using the console's shared verb vocabulary, order, mode/status, result, claim marker and first note line. It runs before CLI intake and changes no producer decisions or actions.


`alba web` and `alba serve` answer on **127.0.0.1 only**. Everything below is under `/api/`; the shapes are the types in [`src/api/types.ts`](../../src/api/types.ts) (a front end imports them; the file has no imports). The old server-rendered board stays at `/legacy`.

## General rules

- Bodies are JSON (`content-type: application/json`), answers are JSON, times are ISO 8601 in UTC.
- A field that is not known is left out (never `null`).
- Every call that reads or writes orders takes `project=<id>` (query for reads, `project` in the body for writes). It may be left out when exactly one project is served; with several, leaving it out is a `bad_request`.
- **Errors**: HTTP status 400, 401, 403, 404, 409, 413 or 500 with `{ "error": { "code", "message" } }`. Codes: `bad_request` (400, a wrong parameter), `unauthorized` (401, only with `--sign-in`: no key and no signed-in session), `forbidden` (403: wrong host or origin, or a request another site made), `not_found` (404), `conflict` (409: the action is not allowed in the order's stage, the order or file exists already), `too_large` (413), `internal` (500). `message` is text for a person.
- **Host check**: the `Host` header must be `127.0.0.1:<port>` or `localhost:<port>`; any other host (a DNS rebinding attempt) gets 403.
- **Access**: by default no sign-in: the server answers only on 127.0.0.1 and refuses pages of other sites (below), which is the boundary on one person's machine. With `--sign-in`, every call under `/api/` and every page under `/legacy/`, reads included, needs the console key in the header `x-alba-token` (a program) or the session cookie of a signed-in browser; without one the answer is 401 (`/legacy` pages send the browser to `/login`). See "Access" below.
- **Other sites**: a request whose `Sec-Fetch-Site` is `cross-site` or `same-site` (a page of another site, or of another port of this machine) is refused with 403 before anything is read or done, unless its `Origin` was given with `--allow-origin`. Every call that changes something is a `POST` or `PUT`; no `GET` changes state.
- **Writes** (`POST`, `PUT`) also need, when the request carries an `Origin` header, an origin of this server (`http://127.0.0.1:<port>` or `http://localhost:<port>`, or one given with `--allow-origin`). A write from a browser (a session cookie, or a `Sec-Fetch-Site` header) must carry an allowed `Origin` (a browser always sends one); a write with the key, or from a program that sends neither header, may leave it out.
- Writes go through the same service layer as the command line; events they record have `by: "web"`.

## Access

By default the console has no sign-in. Any program and browser on this machine may use it, as they could before the key existed; what keeps other sites out is the host check, the `Sec-Fetch-Site` refusal and the `Origin` rule for writes above, and the console page's content security policy. A `/login` link (an old bookmark) goes straight to its page.

With `alba serve --sign-in` (or `alba web --sign-in`), for a machine other accounts use too, the console asks for a key:

Each start of `alba web` or `alba serve` makes a new **console key** (64 hex characters). The key is never part of an answer. It is in two places only:

- the **sign-in link** the command prints when it starts: `http://127.0.0.1:<port>/login?key=<key>`;
- the **key file** `console-<port>.json` (`{port, pid, started, key}`) in a folder only your OS account can read: `ALBA_RUNTIME_DIR` when set, else `%LOCALAPPDATA%\alba\run` on Windows, `$XDG_RUNTIME_DIR/alba` or `~/.alba/run` elsewhere (folder mode 0700, file mode 0600). It is removed when the process stops.

A **browser** opens the sign-in link (or `/login`, and pastes the key into its form). `/login` trades the key for a session cookie `alba_session_<port>` (`HttpOnly; SameSite=Strict; Path=/`) and goes on to the page it was asked for (`next`, a path of this server). The page never sees the key or the cookie. `POST /logout` ends the session. Sessions live in the server process, so after a restart the browser signs in again with the new link. `/login` refuses a request another site made (`Sec-Fetch-Site`).

A **program** of the same account (a script, `alba producer session start` while `alba serve` runs) reads the key file of the port and sends `x-alba-token: <key>`.

With the front end's dev server (`pnpm -C ui dev`), open `http://localhost:5173/login?key=<key>`: the dev server passes `/api`, `/login` and `/logout` to `alba serve`, so the cookie belongs to the dev page. It rewrites an `Origin` only when it is the dev page's own origin; any other `Origin` reaches the server as it is and is refused.

## The stream

`GET /api/stream?project=&logs=&transcripts=` is Server-Sent Events (`text/event-stream`). One connection follows one project. `logs` is a comma-separated list of run keys (`<key>` or `<key>@<offset>`) whose raw log lines are pushed (`logs=SP2:r1,MA1C:r2`); `transcripts` is a comma-separated list of run keys (`<key>` or `<key>@<seq>`) whose new and updated transcript entries are pushed; everything else is always sent.

Event names and their data (types in `StreamEvents`):

| Name | When |
|---|---|
| `hello` | first, once per connection: `{boot, project, at, replayed}` |
| `resync` | the `Last-Event-ID` is from another process or too old: read the lists again |
| `order.added`, `order.updated`, `order.action`, `order.report` | an entry was appended to the event log (`order-added`, `order-updated`, `action-*`, `report`) |
| `run.start`, `run.updated`, `run.end` | `run-start`, `run-updated`, `run-end` entries |
| `check.done`, `refs.adopted` | `check`, `refs-adopt` entries |
| `log.other` | any other entry type |
| `run.log` | new lines at the end of a subscribed run's log: `{project, key, lines, offset}` |
| `run.transcript` | new and state-changed `TranscriptEntry` items for a subscribed run: `{project, key, entries}` |
| `quota` | a new quota reading was written |
| `tick.done` | a tick finished: `{source: schedule\|finish\|api\|start, real, exitCode, done, problems}` |

The server watches the state folder (`events.jsonl`, `quota-history.jsonl`) and the subscribed log files with file-system watchers plus a slow safety check; it does not poll a database. A `: ping` comment is sent every 20 seconds.

**Replay.** Each message has `id: <boot>.<n>`, `n` counting up within the process. The server keeps the last 2000 messages (not `run.log` or `run.transcript`). A client that reconnects sends `Last-Event-ID` (the browser's `EventSource` does it by itself); if the boot part is the same and `n` is still in the buffer, everything after it is sent again, then `hello` says how many were replayed. Otherwise the server sends `resync` and the client reads the lists again. Run log lines and transcript entries are not replayed: a client that wants them reads `GET /api/runs/:key/log` or `GET /api/runs/:key/transcript` after reconnecting.

## `alba serve`

```
alba serve --project alba.yaml [--project other.yaml] [--workers workers.yaml] [--port 4777] [--every 15] [--allow-origin http://localhost:5173]
```

One foreground process that does three things:

1. the board and the interface (`ui/dist` is served when it exists; `/legacy` is the old board);
2. a real tick every `--every` minutes (`0` turns the loop off: interface only);
3. **on an event**: when the process of a run the tool started ends, its end is recorded at once and one tick follows within a minute (with the same caps and quota rules).

A state folder is served by one `alba serve` only: `serve.lock` in it holds the process id; the lock of a process that is gone is taken over. A scheduled `alba tick` (or `alba tick --every`) that finds the lock prints one line, records one `tick-skipped` event on `*` and ends with exit 0. `--every 0` serves the interface only (nothing is started by the process: the event trigger still records ends). Stop it with Ctrl+C.

**Threads.** HTTP, the event stream and writes run on the main thread. Each project has a thread of its own for its ticks, end checks, file polling and producer passes, so a slow step of one project (a provision command, git, a quota command) never holds up another. Projects served together share the workers file: a worker's `concurrency` counts the open runs of every project, and a start records its run under a lock all project threads take, after checking the worker's runs again. GET reads go to two reader threads: one for reads that can take seconds (`/api/clean`, `/api/usage...`, `/api/skills`, `/api/roles`, `/api/lessons`), one for the rest. The board's view of workers, availability and problems comes from each project's last real tick, with orders and running counts read at the time of the request.

The process writes with the actor `serve`; what the board's buttons do is `web`; the command line is `cli`.

**Event-triggered ticks ().** Besides the timer (`--every`) and the end of a run, a tick follows within a few seconds (`tick.done` with `source: "event"`) when any process, the command line included, writes one of these entries to the event log: `order-added`, `order-updated`, `action-queue`, `action-release`, `action-rework`, `action-answer`, `action-approve`, `action-cancel`, `action-hold`, `report`, `run-end`, `question-answered`. Entries written by serve itself or by a tick start nothing, and triggers within 3 seconds of each other make one tick. A changed dispatch table (`dispatch_table.file`) is imported once it has been quiet for 3 seconds (a `serve.notice` of kind `table-imported`, or `table-import-failed` with the reason and the state untouched), then a tick follows. Ticks read a slow quota command at most once a minute (memory is read for every tick).

**Reloading configuration.** serve reads `workers.yaml` and each project's `alba.yaml` again when they change (the file must have been quiet for 3 seconds). The new file is validated first: if it is valid it replaces the old one (`serve.notice` kind `config-reloaded`, and a tick follows so that orders held back by the old limits are looked at again); if not, the old one stays in use, a `config-invalid` notice is sent, and the overview's `problems` carries a line of kind `config` until the file is fixed. A changed project `id` or `state_dir` needs a restart and is refused the same way. `ServeOptions.reloadConfigs: false` switches it off.

## Money, answers and new orders

- **Usage.** Every `Run` has `usage`: tokens (Codex: a total; Grok CLI: tokens with the input/output split, turns and the cost in dollars; OpenCode `--format json`: the split, summed over steps, and the cost), or `source: "unknown"`. An order's `spend` adds its runs up. A worker's `price` (private workers file) turns tokens into a cost marked `cost_estimated`; without a price and without an engine figure `cost_usd` is left out. `mandate.spend_cap` (dollars) stops the tick from starting that order again; `daily_cap_usd` on a worker stops anything new on it for the day; both show as problems of kind `spend`.
- **`answer`.** An order that waits on a question (`awaiting-user`, or `blocked`) is answered with `{action: "answer", text}`. The answer is stored (the order goes back to `queued`, like a rework) and the same worker is started at once: when its launch template has `session` arguments (Grok CLI, Codex with the `resume` arguments of document 003) the old session continues and is told only the answer; otherwise a new run starts whose prompt carries the question and the answer. If the worker cannot be started by the tool (card-only), the answer waits for the next round. Command line: `alba answer <TAG> --text ...`.
- **New orders.** `POST /api/orders` and `alba orders add` share one service. With `body` (`--body-file`) the Markdown is written as `<work_orders>/<TAG>-<slug>.md` with the mode that refuses an existing file; the order is refused before anything is written when the tag or a file for that tag exists. `queue: true` queues it. When the project's `dispatch_table` has `write_back: true` a row is added to the table (a backup goes to `<state_dir>/backups/` first); if the table changed by hand since the last import the row is skipped and `tableWarning` says so.

## Static files

`ui/dist` of this repository (or `uiDir`) is served when it exists, without any sign-in (it holds no secret): `index.html` comes with a Content-Security-Policy (scripts of this server only, plus the page's own inline scripts by their hash; no frames, plugins or other sites), a path without an extension returns the index page (the page does its own routing), a path that leaves the folder is 404. Without `ui/dist`, `/` is a short page pointing to `/legacy` and `/api`.

### Language

Texts the server writes for people (the reason for a stage, check names, problem lines, action messages, error messages) are returned in the language the request asks for: `?lang=zh|en`, else the header `x-alba-lang`, else `Accept-Language` (`zh*` is Chinese), else `ALBA_LANG`, else English. `Session.lang` says what a call without a preference gets. The Chinese words are the ones in `src/i18n-zh.ts` (they follow `docs/glossary.md`); a text without a Chinese entry comes back in English. Stable words (stage names, kinds, outcomes) are never translated.

## Idempotent writes

Every mutating API request (`POST`, `PUT`, `PATCH`, `DELETE`) accepts an optional `Idempotency-Key` header of 1 to 100 characters matching `[A-Za-z0-9_-]`. Requests without the header behave as before; an invalid header returns `400` (`bad_request`).

- **First request**: claims the key (`in_progress`), runs the handler, and stores a durable receipt (key, HTTP method, route path, SHA-256 of the canonical JSON body with sorted object keys, HTTP status code, and JSON response body) in SQLite (`idempotency_receipts`, schema version 8) or `_idempotency.json` on the file backend. Responses with status `>= 500` release the claim so the client may retry safely.
- **Replay**: a later request with the same key, method, route and canonical body returns the stored status code and response body with header `Idempotent-Replay: true` without running the action again.
- **Mismatch**: reusing the same key with a different method, route or body returns `409` with error code `request_mismatch` and does nothing.
- **In progress**: a concurrent request arriving while the first request under the same key is still running returns `409` with error code `request_in_progress` and does nothing.
- **Expiry**: receipts older than 24 hours are removed on the next idempotent write.

The console's shared request helper (`ui/src/lib/api.ts`) sends a fresh `Idempotency-Key` for each mutating action and reuses the same key across automatic retries on network errors or 5xx responses.
### Console attention

Order summaries and details include the newest attention point (`attention.at`, `reason`, `text`), the shared `seen` timestamp, `unread`, and `muted` when enabled. Stage entries, unanswered questions and run endings can raise attention.

| POST route | JSON body | Result |
|---|---|---|
| `/api/orders/:tag/seen` | `{ project, at }` | Advances seen to the supplied timestamp if newer. |
| `/api/seen` | `{ project, tags? }` | Marks each listed order, or every order when omitted, at its current point. |
| `/api/orders/:tag/mute` | `{ project, muted }` | Sets the order's notification preference. |

These routes return `{ "ok": true }`. Unknown tags return 404, including in a batch. Browsers share marks within each project.

The first mark creates SQLite schema 9 with the `order_attention(tag, seen_at, muted)` table. File state uses `_order-attention.json`. State migration and export preserve both fields.

The stream emits `attention.changed` with the project and, for a single-order write, the tag. An open run includes `liveness` and an activity age in `quietMinutes` when known. Runs with a configured slot port allocation also include `ports: { first, last }` (inclusive).
